# Performance telemetry

Use this methodology only for the bounded issue-boundary maintenance checkpoint.

- Inspect the supplied, bounded loop and quality telemetry before proposing a change.
- Attribute an anomaly to a Pi-next or workflow cause; protect product behavior,
  issue requirements, tests, ownership, verification, and archive state.
- Prefer no change. If evidence supports an action, make at most one measurable,
  reversible correction and state the regression guard.
- Keep evidence concise and sanitized: no prompts, transcripts, secrets, or raw
  logs. Treat missing optional consumer methodology as insufficient evidence,
  not as permission to invent a policy.
- A TypeScript change affects a later extension generation; never claim that the
  currently loaded module hot-reloaded.
